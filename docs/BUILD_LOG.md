# mcp-doctor build log

The full narrative history of how `mcp-doctor` was built, dogfooded and fixed: what each real-world run found and what changed because of it. It moved here from the [profile README](https://github.com/vishalhabib99) on 2026-09-23 so the profile stays short. The text is unchanged.

static-analysis CLI that audits MCP server implementations for the things that break an agent calling them (`pip install mcp-server-lint`, or a [GitHub Marketplace Action](https://github.com/marketplace/actions/mcp-doctor)). Dogfooded against 40+ real MCP servers in the wild — up to 76k★, including official servers from GitHub, HashiCorp, Red Hat, Brave, MathWorks, and the MCP spec's own reference servers — found and fixed 43 genuine bugs. Two external contributors independently confirmed real bugs and fixes, including a founder who adversarially tested it via Codex twice on the official spec's own feedback thread; one fix shipped as a [merged PR](https://github.com/homeassistant-ai/ha-mcp/pull/2327) into a 4.8K★ repo. Live [public leaderboard](https://vishalhabib99.github.io/mcp-doctor/) scores every audited repo by quality + security grade, with drift tracking on every re-scan.

found and fixed 45 genuine bugs, verified against each repo before/after, including two real security-heuristic false positives (a plain `RegExp.exec()` call and Playwright's `$eval()` DOM helper both misflagged as dangerous code execution) caught auditing `arabold/docs-mcp-server`, and a false "no description" on two real tools caught auditing `oraios/serena` (29K★) — the tool's description was being read from the wrong docstring, verified directly against serena's own registration code. One fix led to a [merged PR](https://github.com/homeassistant-ai/ha-mcp/pull/2327) into `ha-mcp` (4.8K★, active); a separate clean pass surfaced a real doc-coverage gap [filed upstream](https://github.com/haris-musa/excel-mcp-server/issues/158) in `excel-mcp-server` (4.1K★, active). Added a **read-only annotation-mismatch check** — flags a tool declaring `readOnlyHint: true` whose own code contains a real write signature (raw SQL mutation, a file opened for writing, a mutating HTTP call) — a real, recurring bug class, not hypothetical: `mcp-fuzz`'s own `codebase-memory-mcp#2118` finding below found 13 of 15 tools mislabeled this exact way. Most recently, added `--diff-against`, a schema/contract diff mode: saves a run's tool signatures as a baseline and catches a breaking change later — a tool that's gone, a parameter that's gone, or one that's newly required — the exact gap a real commenter on the trilogy LinkedIn article (Tyler Robinson) named directly ("contract consistency"). Verified against real git history, not just synthetic fixtures: diffed `jingcheng-chen/rhinomcp` 20 commits behind its own `main`, honestly clean (tools added, none removed). Live results: a [public leaderboard](https://vishalhabib99.github.io/mcp-doctor/) ranking every audited repo by quality + security grade, each with a real per-repo badge maintainers can embed in their own README — now with **drift tracking**, comparing every re-scan against whatever was live before it so a regression shows a real ▲/▼ delta instead of silently overwriting the old score. Caught a real cross-environment gotcha while verifying it (a Python 3.11-vs-3.12 parsing difference reading as a false "regression" locally, confirmed harmless since production scans are always 3.12-vs-3.12) — traced to root cause and documented rather than shipped blind. Then ran the full toolkit — every check across all three tools — against one fresh, real target at once for the first time: `sooperset/mcp-atlassian` (5.9K★, real Jira/Confluence integration), 98 tools, 100%/A quality, 99%/A security, `--diff-against` a commit 30 revisions back honestly clean. Also added an **unpinned-dependency (supply-chain) check** — flags a `requirements.txt`/`package.json` dependency with no version floor at all, excluding `>=`/caret/tilde ranges (standard practice, not a real signal on their own) to keep it low-noise — verified clean against six real repos. Then, dogfooding `sooperset/mcp-atlassian` and `jingcheng-chen/rhinomcp` found the tool-name-uniqueness check had no concept of *which server* a tool belongs to — it flagged real, non-duplicate tools as spec violations whenever a repo composed multiple FastMCP servers (`.mount(x, namespace=...)`) or shipped independent standalone entrypoints alongside the real one, a monorepo pattern. Fixed both: resolved `.mount()` calls to apply the real namespaced tool name before the dedup check, and scoped the check to each standalone `if __name__ == "__main__"` entrypoint separately — 11 of 12 false duplicates across the two repos cleared, the one remaining a genuine cross-file FastMCP-instance alias correctly left flagged rather than guessed at. Then, fixed the first bug an external contributor found rather than one this project's own dogfooding surfaced: [Edward Izgorodin](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3322) reported that `--diff-against` falsely flagged a shared, unchanged, required parameter as removed whenever the baseline and current run used two different Python tool-registration styles (a FastMCP-decorated function vs. the raw `Tool(inputSchema=...)` constructor) — the raw-schema style never extracted parameter names to compare in the first place, so "coverage not attempted" silently read as "no parameters." Fixed at the source, with his exact repro kept as a permanent regression test, shipped as v0.9.3. Most recently, a second real report from the same discussion thread: [Christian Bru](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3322) pointed out that the spec's own doc comment on `destructiveHint` says it's meaningful only when `readOnlyHint == false`, but nothing in the JSON Schema enforces that — so a tool can declare `readOnlyHint: true` and an explicit `destructiveHint` at the same time, a combination the spec defines as having no meaning at all, and a realistic copy-paste mistake when a new tool is cloned from an existing write-tool's annotation block. Added a new **annotation-contradiction check** flagging exactly that pair regardless of `destructiveHint`'s value, shipped as v0.9.4. Most recently, turned the description-quality and annotation-contradiction checks into a live registration gate (`check_tool_registration`, v0.10.0) — checks a tool's live `tools/list` metadata instead of parsing source, dependency-free and connection-free (mcp-doctor has never made a live call to anything; this doesn't change that). Dogfooding it against the real official `server-memory` reference server before shipping found the direct port of the static rule (flag `destructiveHint` merely being *present*) false-positived on every tool — that server explicitly sets all four annotation fields as good practice, not a bug. Fixed to require `destructiveHint` actually be `true`, not just present; re-verified 0/9 false positives afterward. Completes the trilogy's live-agent surface: `mcp-doctor` now gates registration, `mcp-fuzz` gates latency, `mcp-reality-check` gates correctness — one live check per original tool. Most recently, added a **URL-format-hint check**: a `url`-shaped string parameter (`url`, `icon_url`, `target_url`, etc.) with no `format: "uri"` JSON-schema hint gives a schema-only client no signal it needs to be a real URL, not just any string — found for real by dogfooding [mcp-fuzz](https://github.com/vishalhabib99/mcp-fuzz) against `jon-the-dev/linkding-mcp-server` ([issue #73](https://github.com/jon-the-dev/linkding-mcp-server/issues/73)), then confirmed to recur independently across `sooperset/mcp-atlassian`, `homeassistant-ai/ha-mcp`, `MODSetter/SurfSense`, `0x4m4/hexstrike-ai`, and `CursorTouch/Windows-MCP` before shipping it as a check. Released as `v1.11.0` / PyPI `0.11.0`. Most recently, fixed a second real report from the same [Edward Izgorodin discussion thread](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3322): after verifying the earlier `--diff-against` fix shipped, he found that a raw-schema property whose key isn't a string literal (a variable used as a dict key) still couldn't be attributed a name, so a genuinely-present parameter was reported as removed when diffed against a baseline that did resolve it. Added a `param_names_complete` coverage flag, consulted before trusting an absence as a real removal — released as `v1.9.5` / PyPI `0.11.1`. Most recently, closed an already-documented, self-found limitation rather than another external report: the description-length heuristic (`<10 chars → likely restates the name`) misfired on complete, well-formed CJK descriptions (e.g. 9 Chinese characters conveying a full sentence, on `xpzouying/xiaohongshu-mcp`), since it was calibrated for English character density. Fixed with a `description_display_width` helper — the same convention terminals and `wcwidth` use, weighting a Wide/Fullwidth character as 2 display columns — applied across the Python, Go, and TS analyzers and the live registration gate. Released as `v1.9.6` / PyPI `0.11.2`. Most recently, fixed a real false positive found dogfooding a fresh target, [`blazickjp/arxiv-mcp-server`](https://github.com/blazickjp/arxiv-mcp-server) (3.1k★, not previously audited): the dangerous-exec security check flagged `scripts/smoke_installed_wheel.py`, a release smoke-test that installs a built wheel into a throwaway venv via fixed, non-tool-derived `subprocess.run()` calls, as if it were reachable tool code. Broadened the existing test-file exclusion to also recognize a `scripts/` path component — breadth-checked first (`aws/chalice`, `colobot/colobot`, `diem/diem` all follow the same convention) rather than treating one repo as enough evidence. 90%→97%/A security on that repo. **2026-09-29, `v1.12.2` / PyPI `0.12.2`:** fixed a real false positive found dogfooding [`mrexodia/ida-pro-mcp`](https://github.com/mrexodia/ida-pro-mcp) (12k★). Its tools document parameters as `Annotated[str, "Address(es) to add breakpoints at"]`, a plain string rather than `Field(description=...)`, and the param-docs check only accepted the `Field` form, so 79 of 93 tools were flagged as undocumented. Whether that string actually reaches the model depends on the framework, so this was checked by listing a real tool's `inputSchema` rather than assumed: standalone `fastmcp` 3.4.7 keeps it as the parameter description, ida-pro-mcp's own `zeromcp` does too (read from its source), but the official MCP Python SDK drops it in both 1.30 (`mcp.server.fastmcp`) and 2.1 (`mcp.server.mcpserver`), because pydantic ignores bare-string metadata. The check now accepts the plain-string form unless the repo uses the official SDK without standalone `fastmcp`; there, the warning names the affected parameters and says the SDK drops them, since an author writing that form reasonably thinks the parameter is documented. 79 → 17 warnings on ida-pro-mcp (the 17 left take a TypedDict whose fields are documented but the parameter itself isn't, a separate case left as is). Before/after on the other 24 local targets: no change in any warning count. 5 new tests, 253 pass.

**2026-09-29, `v1.12.3` / PyPI `0.12.3`:** a second false positive from the same [`mrexodia/ida-pro-mcp`](https://github.com/mrexodia/ida-pro-mcp) run. It was flagged for declaring `idb_open` and `idb_list` twice, but one copy is on the supervisor server and one on the worker server it spawns as a separate process. The existing rule already treats a file that runs its own server from `if __name__ == "__main__":` as a separate server, but only when `run()` was called inline; both ida files use `if __name__ == "__main__": main()`. The rule now also follows a same-file function that starts a locally created instance (`run`, `serve` or `stdio`). Widening it had a real risk: many single-server repos start from `main()` while other modules import the instance and register more tools on it, and those must still count as one server. So a file whose instance another file imports is never treated as standalone, and a test proves a duplicate across the two files is still caught (it fails if that guard is removed). Before/after on 28 local targets: only ida-pro-mcp changed; the genuine `httpx_probe` duplicate in hexstrike-ai and rhinomcp's `join_surfaces` are still flagged.

**2026-09-30, `v1.12.4` / PyPI `0.12.4`:** the first bug found by an outside user rather than by dogfooding. Christian Bru opened three [scan requests](https://github.com/vishalhabib99/mcp-doctor/issues?q=label%3Ascan-request) on 2026-09-29. For [`bruchris/canvas-lms-mcp`](https://github.com/bruchris/canvas-lms-mcp) (#3), a 165-tool TypeScript server, mcp-doctor found 0 tools and still replied with Quality A / Security C. Its tools are plain `{ name, description, inputSchema, handler }` objects returned in `ToolDefinition[]` arrays and registered by one loop, `server.registerTool(tool.name, ...)`, whose property-accessed args can't be resolved at that call site. mcp-doctor now recognizes such an object directly when it sits in an array or const (a same-shaped call argument doesn't count) and skips any name another registration style already found, so nothing is double-counted. Error handling isn't checked for this style because the catch lives in the loop's shared wrapper (`buildHandler`), not each handler. 0 → 166 tools (the 166th, `resolve_pseudonym`, is only registered in FERPA mode, per the repo's README), 100%/A quality, 98%/A security. Before/after on the 25 other local targets: no change in tool count, grade or score. Two scan-by-issue fixes shipped with it: a reply no longer shows grades when 0 tools are found (a grade on nothing read as a real result), and a re-scan of an edited or reopened request now updates the earlier report instead of posting a second one (#5 got two, because the requester edited the issue to opt in to the leaderboard). 5 new tests (2 fail without the fix), 260 pass.

**2026-09-30, `v1.12.7` / PyPI `0.12.7`:** the first planned framework sweep: find every public repo on one MCP framework, then compare mcp-doctor against an independent count. **2026-09-30, `v1.12.8` / PyPI `0.12.8`:** second framework sweep, [`mark3labs/mcp-go`](https://github.com/mark3labs/mcp-go). GitHub code search on `go.mod` reports about 5,900 dependents and returns a sample of 187; 175 were cloned (12 over 150 MB skipped), 127 of them with tools a regex could count (`mcp.NewTool("name"` / `mcp.Tool{Name: "name"`). Recall was 954 of 1,765 (54%), the worst yet. The Go analyzer only counted a `mcp.NewTool(...)` it could trace to an `AddTool` call, but most repos build the tool in a helper function, another file or a registry: `s.AddTool(cpu.NewTool(), cpu.Handler)` (seekrays/mcp-monitor), `filter.AddTool(s, tool, h)` (nguyenvanduocit/jira-mcp), `Registry.Register(&AddHost{})` (blakerouse/ssh-mcp). Every `NewTool(...)` call and bare `Tool{...}` literal on the package imported from `github.com/mark3labs/mcp-go/mcp`, under any alias, is now a definition site on its own; names already reported by a traced path are skipped.
