# mcp-doctor build log

The full narrative history of how `mcp-doctor` was built, dogfooded and fixed: what each real-world run found and what changed because of it. It moved here from the [profile README](https://github.com/vishalhabib99) on 2026-09-23 so the profile stays short. The text is unchanged.

static-analysis CLI that audits MCP server implementations for the things that break an agent calling them (`pip install mcp-server-lint`, or a [GitHub Marketplace Action](https://github.com/marketplace/actions/mcp-doctor)). Dogfooded against 40+ real MCP servers in the wild — up to 76k★, including official servers from GitHub, HashiCorp, Red Hat, Brave, MathWorks, and the MCP spec's own reference servers — found and fixed 43 genuine bugs. Two external contributors independently confirmed real bugs and fixes, including a founder who adversarially tested it via Codex twice on the official spec's own feedback thread; one fix shipped as a [merged PR](https://github.com/homeassistant-ai/ha-mcp/pull/2327) into a 4.8K★ repo. Live [public leaderboard](https://vishalhabib99.github.io/mcp-doctor/) scores every audited repo by quality + security grade, with drift tracking on every re-scan.

found and fixed 45 genuine bugs, verified against each repo before/after, including two real security-heuristic false positives (a plain `RegExp.exec()` call and Playwright's `$eval()` DOM helper both misflagged as dangerous code execution) caught auditing `arabold/docs-mcp-server`, and a false "no description" on two real tools caught auditing `oraios/serena` (29K★) — the tool's description was being read from the wrong docstring, verified directly against serena's own registration code. One fix led to a [merged PR](https://github.com/homeassistant-ai/ha-mcp/pull/2327) into `ha-mcp` (4.8K★, active); a separate clean pass surfaced a real doc-coverage gap [filed upstream](https://github.com/haris-musa/excel-mcp-server/issues/158) in `excel-mcp-server` (4.1K★, active). Added a **read-only annotation-mismatch check** — flags a tool declaring `readOnlyHint: true` whose own code contains a real write signature (raw SQL mutation, a file opened for writing, a mutating HTTP call) — a real, recurring bug class, not hypothetical: `mcp-fuzz`'s own `codebase-memory-mcp#2118` finding below found 13 of 15 tools mislabeled this exact way. Most recently, added `--diff-against`, a schema/contract diff mode: saves a run's tool signatures as a baseline and catches a breaking change later — a tool that's gone, a parameter that's gone, or one that's newly required — the exact gap a real commenter on the trilogy LinkedIn article (Tyler Robinson) named directly ("contract consistency"). Verified against real git history, not just synthetic fixtures: diffed `jingcheng-chen/rhinomcp` 20 commits behind its own `main`, honestly clean (tools added, none removed). Live results: a [public leaderboard](https://vishalhabib99.github.io/mcp-doctor/) ranking every audited repo by quality + security grade, each with a real per-repo badge maintainers can embed in their own README — now with **drift tracking**, comparing every re-scan against whatever was live before it so a regression shows a real ▲/▼ delta instead of silently overwriting the old score. Caught a real cross-environment gotcha while verifying it (a Python 3.11-vs-3.12 parsing difference reading as a false "regression" locally, confirmed harmless since production scans are always 3.12-vs-3.12) — traced to root cause and documented rather than shipped blind. Then ran the full toolkit — every check across all three tools — against one fresh, real target at once for the first time: `sooperset/mcp-atlassian` (5.9K★, real Jira/Confluence integration), 98 tools, 100%/A quality, 99%/A security, `--diff-against` a commit 30 revisions back honestly clean. Also added an **unpinned-dependency (supply-chain) check** — flags a `requirements.txt`/`package.json` dependency with no version floor at all, excluding `>=`/caret/tilde ranges (standard practice, not a real signal on their own) to keep it low-noise — verified clean against six real repos. Then, dogfooding `sooperset/mcp-atlassian` and `jingcheng-chen/rhinomcp` found the tool-name-uniqueness check had no concept of *which server* a tool belongs to — it flagged real, non-duplicate tools as spec violations whenever a repo composed multiple FastMCP servers (`.mount(x, namespace=...)`) or shipped independent standalone entrypoints alongside the real one, a monorepo pattern. Fixed both: resolved `.mount()` calls to apply the real namespaced tool name before the dedup check, and scoped the check to each standalone `if __name__ == "__main__"` entrypoint separately — 11 of 12 false duplicates across the two repos cleared, the one remaining a genuine cross-file FastMCP-instance alias correctly left flagged rather than guessed at. Then, fixed the first bug an external contributor found rather than one this project's own dogfooding surfaced: [Edward Izgorodin](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3322) reported that `--diff-against` falsely flagged a shared, unchanged, required parameter as removed whenever the baseline and current run used two different Python tool-registration styles (a FastMCP-decorated function vs. the raw `Tool(inputSchema=...)` constructor) — the raw-schema style never extracted parameter names to compare in the first place, so "coverage not attempted" silently read as "no parameters." Fixed at the source, with his exact repro kept as a permanent regression test, shipped as v0.9.3. Most recently, a second real report from the same discussion thread: [Christian Bru](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3322) pointed out that the spec's own doc comment on `destructiveHint` says it's meaningful only when `readOnlyHint == false`, but nothing in the JSON Schema enforces that — so a tool can declare `readOnlyHint: true` and an explicit `destructiveHint` at the same time, a combination the spec defines as having no meaning at all, and a realistic copy-paste mistake when a new tool is cloned from an existing write-tool's annotation block. Added a new **annotation-contradiction check** flagging exactly that pair regardless of `destructiveHint`'s value, shipped as v0.9.4. Most recently, turned the description-quality and annotation-contradiction checks into a live registration gate (`check_tool_registration`, v0.10.0) — checks a tool's live `tools/list` metadata instead of parsing source, dependency-free and connection-free (mcp-doctor has never made a live call to anything; this doesn't change that). Dogfooding it against the real official `server-memory` reference server before shipping found the direct port of the static rule (flag `destructiveHint` merely being *present*) false-positived on every tool — that server explicitly sets all four annotation fields as good practice, not a bug. Fixed to require `destructiveHint` actually be `true`, not just present; re-verified 0/9 false positives afterward. Completes the trilogy's live-agent surface: `mcp-doctor` now gates registration, `mcp-fuzz` gates latency, `mcp-reality-check` gates correctness — one live check per original tool. Most recently, added a **URL-format-hint check**: a `url`-shaped string parameter (`url`, `icon_url`, `target_url`, etc.) with no `format: "uri"` JSON-schema hint gives a schema-only client no signal it needs to be a real URL, not just any string — found for real by dogfooding [mcp-fuzz](https://github.com/vishalhabib99/mcp-fuzz) against `jon-the-dev/linkding-mcp-server` ([issue #73](https://github.com/jon-the-dev/linkding-mcp-server/issues/73)), then confirmed to recur independently across `sooperset/mcp-atlassian`, `homeassistant-ai/ha-mcp`, `MODSetter/SurfSense`, `0x4m4/hexstrike-ai`, and `CursorTouch/Windows-MCP` before shipping it as a check. Released as `v1.11.0` / PyPI `0.11.0`. Most recently, fixed a second real report from the same [Edward Izgorodin discussion thread](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/3322): after verifying the earlier `--diff-against` fix shipped, he found that a raw-schema property whose key isn't a string literal (a variable used as a dict key) still couldn't be attributed a name, so a genuinely-present parameter was reported as removed when diffed against a baseline that did resolve it. Added a `param_names_complete` coverage flag, consulted before trusting an absence as a real removal — released as `v1.9.5` / PyPI `0.11.1`. Most recently, closed an already-documented, self-found limitation rather than another external report: the description-length heuristic (`<10 chars → likely restates the name`) misfired on complete, well-formed CJK descriptions (e.g. 9 Chinese characters conveying a full sentence, on `xpzouying/xiaohongshu-mcp`), since it was calibrated for English character density. Fixed with a `description_display_width` helper — the same convention terminals and `wcwidth` use, weighting a Wide/Fullwidth character as 2 display columns — applied across the Python, Go, and TS analyzers and the live registration gate. Released as `v1.9.6` / PyPI `0.11.2`. Most recently, fixed a real false positive found dogfooding a fresh target, [`blazickjp/arxiv-mcp-server`](https://github.com/blazickjp/arxiv-mcp-server) (3.1k★, not previously audited): the dangerous-exec security check flagged `scripts/smoke_installed_wheel.py`, a release smoke-test that installs a built wheel into a throwaway venv via fixed, non-tool-derived `subprocess.run()` calls, as if it were reachable tool code. Broadened the existing test-file exclusion to also recognize a `scripts/` path component — breadth-checked first (`aws/chalice`, `colobot/colobot`, `diem/diem` all follow the same convention) rather than treating one repo as enough evidence. 90%→97%/A security on that repo. Also caught and fixed a real versioning bug while releasing it: the Action's `v1.x` tags had gone non-monotonic since `v1.11.0` (2026-09-18) — three later fixes shipped as `v1.9.5`/`v1.9.6`/`v1.9.7` instead of continuing past it, a numbering mistake, not a branch — confirmed via `git merge-base` that `v1.11.0`'s commit is an ancestor of all three. Deleted the mis-numbered tag/release and re-cut as `v1.11.3`, continuing the correct line. Released as `v1.11.3` / PyPI `0.11.3`. Most recently, fixed a real detection gap found dogfooding a fresh target, [`zcaceres/markdownify-mcp`](https://github.com/zcaceres/markdownify-mcp) (3k★): tools are collected via `import * as tools from "./tools.js"` and returned as `{ tools: Object.values(tools) }` from the low-level SDK's list-tools handler, each wrapped in Zod's `Schema.parse({...})` — neither the namespace-import `Object.values()` shape nor the `.parse()` wrapper were recognized, reporting 0 of 11 tools. Confirmed not a one-off first (`flesler/mcp-tasks` uses the identical `Object.values(tools)` idiom, though via a runtime loop — a separate, still out-of-scope pattern, same class as the already-documented `mcp-server-browserbase` `.forEach()` case) before adding namespace-import resolution and a generic `.parse(...)` unwrap. 0→11 tools, 100%/A quality, 98%/A security. Released as `v1.11.4` / PyPI `0.11.4`. Most recently, fixed a second real detection gap found dogfooding a fresh target, [`MinishLab/semble`](https://github.com/MinishLab/semble) (6.1k★): 21 of 22 dangerous-exec flags were false positives, all in `benchmarks/`/`benchmarks/baselines/` — a performance-comparison harness shelling out to competing CLI tools, not reachable from either of the repo's 2 real MCP tools. Breadth-checked first (`pypa/pipenv`, `pytorch/xla`, `facebookexperimental/hermit` all follow the same convention) before broadening the existing `scripts/` exclusion to also cover `benchmarks/`. 62%/D→88%/B security; the one remaining flag (a `git clone` of a caller-supplied URL in the real indexing code) is genuine and correctly still caught. Released as `v1.11.5` / PyPI `0.11.5`. Most recently, fixed a real false positive found dogfooding a fresh target, [`getsentry/XcodeBuildMCP`](https://github.com/getsentry/XcodeBuildMCP) (6.4k★): a local `const exec = executor ?? getDefaultCommandExecutor();` (a dependency-injected command runner, for testability) was misflagged as `child_process.exec` by the bare-identifier dangerous-exec regex, which can't tell a locally rebound name from the real primitive. Confirmed not a one-off first (the same `const exec = executor ?? ...` idiom recurs independently in `Seitrace/seitrace-mcp`, another real MCP server) before adding a scope-aware shadow check — only the two bare-identifier patterns it can actually rebind are suppressed, the qualified ones (`os.system`, `child_process.exec`, `exec.Command`) are untouched. 45%/F→70%/C security on that repo. Released as `v1.11.6` / PyPI `0.11.6`. Most recently, fixed a real README-coverage false positive found dogfooding [`firecrawl/firecrawl-mcp-server`](https://github.com/firecrawl/firecrawl-mcp-server) (7.5k★): two live, callable tools whose own description opens "Deprecated compatibility entry point..." were flagged as undocumented gaps, when their absence from the README was deliberate — they're compatibility shims that always error/redirect to a replacement. Fixed by skipping a tool from the undocumented-tool check when its own description says it's deprecated, then independently reconfirmed against a second, unrelated codebase, [`exa-labs/exa-mcp-server`](https://github.com/exa-labs/exa-mcp-server) (5k★): 6 genuinely deprecated tools, three different notice styles (`[Deprecated: Use X instead]`, `⚠️ DEPRECATED:`, `[Deprecated]`), all correctly suppressed — leaving exactly one real, still-undocumented tool (`get_code_context_exa`) correctly flagged — [filed upstream](https://github.com/exa-labs/exa-mcp-server/issues/443). Released as `v1.11.7` / PyPI `0.11.7`. Most recently, fixed a real README-coverage false positive found dogfooding the official [`modelcontextprotocol/servers`](https://github.com/modelcontextprotocol/servers/tree/main/src/everything) "everything" protocol-feature test server: its README delegates the full tool list to a linked `docs/features.md` file rather than inlining it, but the undocumented-tool check only ever read the README itself — false-flagging all 18 real tools at once. Fixed by also reading any local `.md` file the README links to (one hop, same-repo relative paths only). Full-trilogy pass on the same target: `mcp-fuzz` and `mcp-reality-check` both came back clean (100%/A), correctly flagging one tool's genuine 10-second delay as slow rather than a false positive — that tool's entire documented job is to simulate a long-running operation. Released as `v1.11.8` / PyPI `0.11.8`. Most recently, fixed a real duplicate-finding bug found dogfooding [`ahujasid/mcp-for-blender`](https://github.com/ahujasid/mcp-for-blender) (29k★): its root-level `addon.py` is bundled verbatim into `src/blender_mcp/bundled/addon.py` so the packaging step can zip it into the distributable Blender plugin, and both byte-identical copies were scanned independently — doubling every `dangerous_exec`/SSRF finding, and since each check's score penalty is capped by occurrence count, pushing a single real `eval`/`exec` call over the cap and inflating the security penalty. Fixed by deduping every scanned file by content hash before either the security scans or tool-finding run, so a duplicated tool-definition file can't double-count a clean tool's score contribution either. 95%→97%/A security on that repo. Released as `v1.11.9` / PyPI `0.11.9`.

**2026-09-29, `v1.12.2` / PyPI `0.12.2`:** fixed a real false positive found dogfooding [`mrexodia/ida-pro-mcp`](https://github.com/mrexodia/ida-pro-mcp) (12k★). Its tools document parameters as `Annotated[str, "Address(es) to add breakpoints at"]`, a plain string rather than `Field(description=...)`, and the param-docs check only accepted the `Field` form, so 79 of 93 tools were flagged as undocumented. Whether that string actually reaches the model depends on the framework, so this was checked by listing a real tool's `inputSchema` rather than assumed: standalone `fastmcp` 3.4.7 keeps it as the parameter description, ida-pro-mcp's own `zeromcp` does too (read from its source), but the official MCP Python SDK drops it in both 1.30 (`mcp.server.fastmcp`) and 2.1 (`mcp.server.mcpserver`), because pydantic ignores bare-string metadata. The check now accepts the plain-string form unless the repo uses the official SDK without standalone `fastmcp`; there, the warning names the affected parameters and says the SDK drops them, since an author writing that form reasonably thinks the parameter is documented. 79 → 17 warnings on ida-pro-mcp (the 17 left take a TypedDict whose fields are documented but the parameter itself isn't, a separate case left as is). Before/after on the other 24 local targets: no change in any warning count. 5 new tests, 253 pass.

**2026-09-29, `v1.12.3` / PyPI `0.12.3`:** a second false positive from the same [`mrexodia/ida-pro-mcp`](https://github.com/mrexodia/ida-pro-mcp) run. It was flagged for declaring `idb_open` and `idb_list` twice, but one copy is on the supervisor server and one on the worker server it spawns as a separate process. The existing rule already treats a file that runs its own server from `if __name__ == "__main__":` as a separate server, but only when `run()` was called inline; both ida files use `if __name__ == "__main__": main()`. The rule now also follows a same-file function that starts a locally created instance (`run`, `serve` or `stdio`). Widening it had a real risk: many single-server repos start from `main()` while other modules import the instance and register more tools on it, and those must still count as one server. So a file whose instance another file imports is never treated as standalone, and a test proves a duplicate across the two files is still caught (it fails if that guard is removed). Before/after on 28 local targets: only ida-pro-mcp changed; the genuine `httpx_probe` duplicate in hexstrike-ai and rhinomcp's `join_surfaces` are still flagged.

**2026-09-30, `v1.12.4` / PyPI `0.12.4`:** the first bug found by an outside user rather than by dogfooding. Christian Bru opened three [scan requests](https://github.com/vishalhabib99/mcp-doctor/issues?q=label%3Ascan-request) on 2026-09-29. For [`bruchris/canvas-lms-mcp`](https://github.com/bruchris/canvas-lms-mcp) (#3), a 165-tool TypeScript server, mcp-doctor found 0 tools and still replied with Quality A / Security C. Its tools are plain `{ name, description, inputSchema, handler }` objects returned in `ToolDefinition[]` arrays and registered by one loop, `server.registerTool(tool.name, ...)`, whose property-accessed args can't be resolved at that call site. mcp-doctor now recognizes such an object directly when it sits in an array or const (a same-shaped call argument doesn't count) and skips any name another registration style already found, so nothing is double-counted. Error handling isn't checked for this style because the catch lives in the loop's shared wrapper (`buildHandler`), not each handler. 0 → 166 tools (the 166th, `resolve_pseudonym`, is only registered in FERPA mode, per the repo's README), 100%/A quality, 98%/A security. Before/after on the 25 other local targets: no change in tool count, grade or score. Two scan-by-issue fixes shipped with it: a reply no longer shows grades when 0 tools are found (a grade on nothing read as a real result), and a re-scan of an edited or reopened request now updates the earlier report instead of posting a second one (#5 got two, because the requester edited the issue to opt in to the leaderboard). 5 new tests (2 fail without the fix), 260 pass.

**2026-09-30, `v1.12.5` / PyPI `0.12.5`:** after the canvas fix, the other 0-tool local targets were checked one by one. Four were already explained or correctly out of scope: `playwright-mcp` (tools live in the Playwright monorepo), `mcp-toolbox` (built from YAML), `pal-mcp-server` (dynamic names), and `21st-dev/magic-mcp` (now a thin stdio-to-HTTP proxy whose tools live on 21st.dev's server). `prest` hand-writes its own JSON-RPC endpoint with per-table tools generated at runtime, a single-repo pattern, declined. One was a real miss: [`cyanheads/clinicaltrialsgov-mcp-server`](https://github.com/cyanheads/clinicaltrialsgov-mcp-server) reported 0 of 7 tools. It's built on `@cyanheads/mcp-ts-core`, whose `tool('name', { description, input: z.object(...), async handler() {} })` takes two args, while the existing `.tool()` path expects three or more. Breadth-checked before adding it: 30+ public servers depend on the framework (GitHub code search on `package.json`), including two outside its author's own; confirmed on `cyanheads/pubmed-mcp-server` (0 → 11) and `magnusquest/startgg-mcp` (0 → 8). Both `description` and `input` are required so the SDK's two-arg `server.tool(name, callback)` can't match (a test proves it). Error handling isn't checked for this style, since the framework's documented rule is "logic throws, framework catches". pubmed also exposed a second, older bug: `description: buildFulltextDescription({...})`, built at runtime, was reported as "Tool has no description". Every TS style now treats a description it can't resolve as unknown rather than missing; a literal empty string is still flagged. One existing test had locked in the old behavior (a `getDescription(...)` call flagged as missing) and was updated on purpose. clinicaltrialsgov 0 → 7 tools, 100%/A quality, 94%/A security. Before/after on 26 other local targets: no change. 3 new tests plus 1 updated (3 fail without the fix), 263 pass.
